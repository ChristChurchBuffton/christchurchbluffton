**Full spec (brief's own text, condensed to essentials — see the source .txt for exact wording before building):**

1. **Clean up the household model.** Add adult birthday (month/day). Admin manual create/edit (paper/contact-card intake). One record per person, every view is a layout over the same data — never a copy.
2. **Public adult/household form.** Hosted on the site. All fields optional except at least one name. Submits into admin as **Pending** (review before merging into live records). Duplicate check on submit: email OR phone + last name → flag for merge, don't auto-create a second household. Permission-gated view (roles TBD by leadership — build permission-ready, matching the existing role/permission pattern already in this admin).
3. **Youth membership — New Student page.** Reachable from check-in's "New Student" button, a direct link, or a QR code.
   - Student section: name, address, student phone, birthday, grade, medical notes.
   - **Student ID auto-generated on submit** (readable format, e.g. `Y-0142`), unique, never reused, parent never types it, shown on the student's record.
   - Parent section below: name, phone, email, address.
   - **Consent & privacy section** below that — student protection policy, volunteer vetting/background checks, privacy, and **photo consent** as its own yes/no choice. Photo consent stores: typed-name signature, date, terms version; shows a visible "no photos" flag on the record; supports revocation and **yearly expiration/renewal**. Final wording/layout TBD, but **the terms text itself must be editable in the admin panel without a code change** (same spirit as the Content Editor's editable-text approach elsewhere in this admin). **The reviewed PDF (`Christ_Church_Child_Photo_Video_Permission_Fillable.pdf`) is the actual consent language/shape to build from** — per-child, separate Yes/No for identifiable photos vs. identifiable video, parent/guardian relationship, typed-name-as-signature + date, explicit "does not permit publishing the child's name with the media," explicit note that permission can be withdrawn but copies already shared may remain outside the church's control.
   - Youth-only data (medical notes, consent, grade) lives in **its own table linked to the student** — not mixed into the general household data.
   - On submit: student added to Youth tab; parent lookup by email/phone+last name (create household w/ parent as head + student as member, OR attach to existing household, updating not duplicating if the student's already there); if submitted during a live check-in session, auto check the student in to that night.
   - Youth admin view shows the student first, parent info below.
4. **Youth check-in.** Youth tab gets an "Access Check In" button. Before opening: leader picks/adds Date-time (defaults now), Youth leader (saved list, reusable), Location (saved list, reusable) → creates a "Youth Night" record. Check-in page (tablet-friendly, big buttons): "Returning Student" (type-ahead name search — **only matching names shown, never the full list or any personal details on this screen**; tap to check in; fallback by Student ID; records Student ID + night + timestamp; blocks double check-in same night; confirmation screen then resets) and "New Student" (opens the page from item 3). **Kiosk-locked** — no admin/record access from that screen; exiting needs admin login or PIN. Attendance tab inside Youth: list of nights (date/leader/location/count) → click for who attended + times; each student's own record shows their attendance history.
5. **Data import.** CSV/Excel → households, with a column-mapping step + dry-run preview before any write; imported rows go through the same duplicate check as the public form.

**Cross-cutting requirements:** admin/internal use only; all public forms mobile-first, work via QR/direct-link/tablet; medical + consent data visible only to a youth-leader role; spam protection (honeypot/Turnstile) on public forms; no member data ever in public pages or client-side code; short privacy/consent line on the adult form; **adult form + whole youth system sit behind a release toggle — launch only at leadership's direction**; **ask before any destructive change to existing Congregation data/schema** (matches this project's own standing rule).

**Build order (brief's own, most logical dependency order):** 1) cleanup + migration, 2) adult/household form + pending review + dedup, 3) New Student page + consent + youth admin view, 4) check-in (sessions, saved leaders/locations, attendance tab), 5) import, 6) permissions/roles.

**Decisions confirmed by Kevin 2026-09-29:** migrate children to real per-child records now (not left jsonb); youth-leader access = a permission flag on the existing Admin/Staff pattern (not a new role tier — not built yet, nothing to gate until Step 3's medical/consent tables exist); release toggle = an on/off switch inside the admin panel (not built yet — folds into Step 2/3 when the actual public forms exist).
